# Riflo frontend

A responsive creative studio with Firebase Google sign-in, Drive connection and selection, a private project library, generation, output downloads and account allowances. Normal mode never substitutes samples for account data.

Run `npm install`, copy `.env.example` to `.env.local`, then run `npm run dev`. Open `http://localhost:4311`. Restart Vite after changing environment settings. Public Firebase web settings come from a registered Firebase web app, not a service account. Enable Google as an Authentication provider and add the development hostname to Firebase Authentication's authorized domains. Sign-in uses Firebase's Google popup; it does not request Drive permissions.

Without Firebase settings, sign-in shows a setup message and remains unavailable. **Explore the preview** works without configuration. Preview renders a separate component tree, initializes no Firebase connection, makes no API calls and stores no account data. Its state selector is for design checks, not simulated processing.

## Local Firebase testing without Blaze

From `../riflo-backend`, start `firebase emulators:start --project demo-riflo` using its existing Firebase configuration. This starts Auth on port 9099, Firestore on 8080, Storage on 9199 and the emulator UI on 4000. Configure the backend from its `.env.example`, including `NODE_ENV=development`, `FIREBASE_PROJECT_ID=demo-riflo` and all three emulator host variables. Run the API on port 4310 using the backend README instructions. The backend needs its normal configuration even when this frontend slice only reads account state.

For the frontend, set `VITE_FIREBASE_PROJECT_ID=demo-riflo`, `VITE_FIREBASE_API_KEY=demo-key`, `VITE_FIREBASE_AUTH_DOMAIN=demo-riflo.firebaseapp.com`, `VITE_FIREBASE_APP_ID=demo-app` and `VITE_FIREBASE_AUTH_EMULATOR_URL=http://127.0.0.1:9099`. The Google popup then uses the local emulator sign-in screen, not a real Google account. The emulator URL is rejected in production builds or if it points outside loopback HTTP.

Frontend and backend must use the **same project ID and Auth emulator**. Emulator tokens are unsigned and cannot be trusted by a real backend. For real Firebase sign-in, remove emulator settings on both sides; the backend requires Application Default Credentials (ADC) provisioned outside this repository. Never use emulator authentication in production. A newly signed-in account has no processing access until an administrator grants it in the backend. Missing or expired access does not redirect or globally block account/read pages.

Vite proxies `/v1` and `/health` to `http://127.0.0.1:4310`, so browsers use one origin and Drive cookies can later use the same origin. Production hosting must forward these paths to the backend and serve `index.html` for application routes. `vite preview` only previews the compiled UI; it is not the production API proxy.

## Checks and structure

`npm run typecheck`, `npm test`, and `npm run build` verify the slice. Tests use substitutes and do not call Firebase cloud or paid AI services. Actual Google popup sign-in and real Firebase account reads require operator configuration and remain unverified here.

The reproducible [browser smoke checks](test/browser/README.md) exercise real browser layouts, keyboard paths, account states and private media using local substitutes. They do not require cloud credentials.

Features live under `src/features`, navigation under `src/app`, shared auth/API/UI pieces under `src/shared`, and visual tokens under `src/styles`. Firebase handles session persistence; the API requests a fresh usable ID token through its SDK and never copies tokens into application storage. Requests are bound to the current account, abort on unmount and reject late responses after account changes. Authorization and limits remain backend-owned.

Color roles are centralized in [`src/styles/tokens.css`](src/styles/tokens.css): Kingfisher primitives feed semantic roles and shared component aliases. Blue (`--primary`) marks actions and focus; copper (`--editorial`) identifies the wordmark dot, existing heading punctuation and output-format labels/ordinals. The selected output uses readable neutral text and a blue selection stripe. Green, red and orange (`--success`, `--error`, `--warning`) describe outcomes with explicit text; async loading stays neutral. Canvas, navigation, cards and reading surfaces stay neutral in both themes. Change palette values in the themed token roots and reuse these roles in shared styles; browser checks verify actual consumers and contrast.

Calistoga and Inter are bundled locally through Fontsource; OFL licenses remain in the installed packages. All `VITE_` values are public browser configuration. Anthropic, Deepgram, Google OAuth client secrets, encryption keys and Firebase Admin credentials belong only in backend secret configuration.

Official references checked for this slice: [Firebase Google sign-in](https://firebase.google.com/docs/auth/web/google-signin), [Auth emulator](https://firebase.google.com/docs/emulator-suite/connect_auth), [Vite proxy](https://vite.dev/config/server-options.html#server-proxy), [React effect cleanup](https://react.dev/reference/react/useEffect).

## Drive and project setup

Set `VITE_GOOGLE_PICKER_API_KEY` and `VITE_GOOGLE_PROJECT_NUMBER` in `.env.local`. These are public browser settings, not secrets. The project number must match the Cloud project containing the backend OAuth client. The backend needs its Google client ID, client secret, redirect URL and encryption key as described in its README. Drive consent is separate from Firebase login and uses only `drive.file`.

The OAuth redirect URL must use the same browser-facing host as Riflo so the browser binding cookie is returned. For the documented Vite setup use `http://localhost:4311/v1/drive/connection/callback` in both Google and backend settings; Vite forwards this route to the backend. Do not mix localhost and 127.0.0.1. The current callback returns JSON; Riflo checks actual connection status from the main window and closes the popup when confirmed. Closing a popup is never treated as success. Popup blocking, cancellation and a five-minute waiting limit are explicit states.

Enable both Google Drive and Picker APIs. Current [Google web Picker sample](https://developers.google.com/workspace/drive/picker/guides/web-picker-sample) recommends restricting the browser key to both APIs and allowing your website referrers plus `https://docs.google.com/*`, where the Picker frame runs. The [integration guide](https://developers.google.com/workspace/drive/picker/guides/web-picker) recommends list mode for narrow scopes without thumbnail access; this implementation uses a video list view. Picker loads only after the user asks to select a video. Its short-lived token stays in memory, never in browser storage or URLs, and the Picker is disposed when cancelled, expired or unmounted. Production hosting security headers must allow the official Google script/frame resources and be verified against live Google sign-in/Picker before enforcement; no CSP bypass or wildcard script policy is added here.

Drive links are parsed into a file ID and optional resource key; the browser does not fetch supplied URLs. Metadata is checked by the backend, and users explicitly confirm before importing. Link access may require selecting the file in Picker first. Actual bytes and duration are inspected during background import. `source_ready` means the original was imported; it does not mean content has been generated. Lists and details poll only during queued/importing states and stop on unmount or terminal state.

An uncertain import response retains its complete original input, checked metadata and request key in account-scoped session storage. Reload restores that same locked request, including Drive resource keys; it never substitutes a new Picker selection. Legacy key-only markers restore their encoded input conservatively. No access tokens are stored; the pending request is removed after confirmed success or a known rejection of the first attempt. A lost response or a marker restored after reload keeps the same request, even if a later retry is rejected. Account reads remain available after access expires. The optional explicit `intake.available` capability gates source preparation, Picker, Drive connection and import; trial eligibility alone cannot enable them. Trial initiation remains gated by backend rollout controls until retention and abuse prerequisites are ready. Backend capabilities determine whether new imports are configured and permitted, and the backend independently enforces all access and limits.

Live Google consent, Drive permissions, Picker and cloud video intake remain unverified until operator configuration and Firebase Storage billing are ready. Deterministic tests do not establish live Google connectivity.

## Content and account views

Each project can request another generation batch after the previous batch finishes: X posts, LinkedIn posts, a blog, a newsletter, a carousel and a short video. Each action requests one output; `/generation/availability` provides per-format eligibility, access expiry, runtime restrictions and temporary writing options. The backend independently checks access and allowances on admission. The project view does not request account usage, capabilities, saved brand or Drive connection status, and uses only the optional shared-credit balance and per-format costs supplied by that project response. Shared-credit accounts see each action’s credit cost and remaining credits; unaffordable actions are disabled while saved content stays readable. Legacy per-format grants retain their existing eligibility flow. A source that is ready to process is distinct from a completed generation. Active work uses finite SSE observation; historical unexpired results remain readable, and uncertain submissions reuse their account/project request identity. Only an exact-key submission response resolves pending generation; reading an older batch cannot discard it. A known first-attempt rejection reopens the action after refreshing availability. Uncertain requests keep their original selection, writing overrides and key. Availability-check failure pauses new generation without blocking saved results. The backend controls original-video and transcript deadlines separately. An expired original can leave transcript-based formats available, while media-dependent requests explicitly ask for importing the video again. No source is silently downloaded again. Failed imports offer same-project retry using backend eligibility and cooldown/Retry-After; pending retry identity survives reload in account/project-scoped session storage. Retry only imports and never starts generation. There are no editing, revision, publishing or checkout controls in this phase.

The project reads its source information, current generation, outputs and project availability. Optional lifecycle deadlines refresh project availability when leftover trial funding expires even while paid access continues. Admission, settlement, expiry and explicit checks refresh availability without fetching account APIs. Saved writing preferences are resolved by the backend at generation time; the browser sends only explicit temporary overrides. Unchanged fields inherit saved preferences, while explicit language/spelling defaults clear just those inherited values. Identical SSE snapshots do not repeat saved-state reads. Progress changes read the current batch; newly ready slots and terminal completion also read outputs, after progress. Reconnection and explicit result refresh still reconcile both, and failed output reads cannot be replaced by an older cached list.

Text is rendered as plain text, not executable HTML. Carousel PNGs and short-video MP4s are fetched through authenticated owner routes, then shown with temporary browser object URLs. URLs are released on unmount and account changes. Downloads do not expose storage paths or put access tokens in URLs. Media remains subject to backend retention.

Usage shows the backend access period in UTC and source time in minutes/seconds. Shared-credit accounts show one creation-credit meter; legacy grants show output counts for all six formats. The server’s accounting discriminator selects the ledger shape; malformed or incomplete shared balances are rejected. Used, in-progress and remaining values come directly from `/v1/usage`; they are not billing estimates. Usage is read even before a trial starts or after access ends; this read never activates a trial. Lifecycle responses show separate trial/paid balances, their original UTC deadlines and renewal/cancellation intent. Combined totals omit a single period ID; individual period ledgers retain their owning IDs. Legacy response shapes remain supported. Existing projects and Drive disconnection remain accessible. Company AI costs are tracked by the backend ledger and have no public dashboard endpoint yet.

Use `?preview=true` on `/projects`, `/projects/sample`, `/usage` or `/connections` for isolated sample views. The sample-state selector includes empty, importing, source-ready, generating, partial, expired and unconfigured states. These samples never contact the backend, grant permissions or generate content. Reduced-motion preferences disable decorative transitions; navigation and forms remain keyboard accessible.

YouTube and Drive share the same import confirmation and generation flow. Available source choices come from `services.sources` in backend capabilities; missing YouTube settings leave Drive usable. YouTube does not require a Drive connection. Paste one public/unlisted video link that you own or may reuse; sign-in, age restrictions, livestreams and browser verification challenges return explicit errors. The browser never embeds or downloads directly from YouTube. Backend tool setup is documented in the backend README.

YouTube metadata is checked through `POST /v1/sources/youtube/validate`; its returned canonical input creates the project. Unknown file size/duration remain visibly unknown until the imported video is probed. Request keys are scoped to the signed-in account and source identity and survive lost responses/reloads. Legacy Drive project data and request keys retain their original format. Preview source choices use illustrative samples and make no live requests. Real YouTube extraction remains unverified; browser tests use deterministic fixtures.

Motion roles live in `src/styles/tokens.css`: controls use 140ms ease-out, real cold loading handoffs use 180ms, route changes use 200ms, and native appearance snapshots use 220ms ease-in-out. `src/shared/ui/motion.ts` owns native opacity/4px entrances: the stable main region enters on navigation, and loading boundaries enter once when data first arrives. Cached mounts, refreshes, counts and polling updates stay still; overlapping parent entrances suppress child entrances. Cancellation never gates rendering, focus, scrolling or requests. Browsers without native animation show the final state immediately.

Theme transitions start only after an effective light/dark change, preserving the head bootstrap and system preference. A native View Transition reveals a complete new scene from top to bottom over the opaque old scene, preserving text/surface contrast throughout; browsers without that API switch immediately. Rapid choices skip previous snapshots, and output selection uses the same content entrance. Existing control hover behavior remains bounded. CSS and native entrances respect reduced motion, including changes while motion is running.
